# Project Memory — Overview

> Single source of truth map for this project's memory bank. Read this first,
> then open only the file you need. The bank describes what the code does and how
> we build it — in prose, tables, and signatures-as-text, never pasted source code.

## How to use

Read the transient state first — `progress.md` (what works / what's left) and
`active-context.md` (what is being worked on right now) — then the durable docs
in this order to understand or rebuild the system bottom-up:

- `architecture/` — module/file layout, layering, dependencies, build + config + env. Read first: the shape to scaffold.
- `data/`         — data model, schema, state, formats, invariants, constants. Read next: the shapes the code moves.
- `interface/`    — public contracts: API, CLI, signatures, events, config keys. Read to know what each unit must expose.
- `behavior/`     — what each unit must do: logic, algorithms, flow, edge cases. Read to fill in the logic.
- `rule/`         — conventions, procedures, how-to ("how we do X"). Read to follow project practice.

Trust each durable statement by its confidence marker: 🟢 `confirmed` (cited from
code), 🟡 `inferred` (deduced — verify against source), 🔴 `gap` (unresolved —
needs a human before you rely on it).

## Conventions

Durable docs follow semantic `kebab-case.md` naming inside their category folder,
with frontmatter (`title`, `category`, `purpose`, `status`, `updated`, `source`,
`confidence`, `keywords`, optional `order`). Look a doc up by theme in `Purpose`
or by exact name in `Keywords`. Reading order comes from the category order above
then the `order` field, not the file name. One concept per file, under ~300
lines, front-load a one-line summary, cite the source path (with `:line` where it
helps), link instead of repeating. The two state files carry only `title` +
`updated` and are exempt from category naming. See the `skill-memory-ai` reference
`memory-doc-rules.md` for the full rules.
